1장. Git과 GitHub로 협업하기

실습문제와 힌트 — 기본 · 필수 · 도전

준비시간1시간 30분개념 지도전체 흐름

먼저 스스로 풀어 봅니다. 막히면 힌트를 하나씩 펼쳐 봅니다. 해답은 수업 시간에 함께 확인합니다. 입문자는 기본 → 필수, 이수자는 필수 → 도전을 목표로 합니다. Git 명령은 손에 익어야 하므로 직접 쳐 보는 것이 중요합니다.

about-me 저장소를 만들고 커밋 3개를 찍은 뒤 내 GitHub에 push한다.

브랜치 두 개로 일부러 충돌을 만들고 해결한다. 이어서 팀 저장소에 PR을 하나 올린다.

실수로 올린 .env 파일을 기록에서 빼는 순서를 정리하고, 왜 키 재발급이 필요한지 설명한다.

문제 1 (기본) — 첫 저장소를 GitHub까지

  1. D:\workspace\about-me 폴더를 만들고 Git 저장소로 만든다.
  2. README.md에 이름, 관심 분야, 목표를 한 줄씩 나눠 추가하며 커밋 3개를 찍는다.
  3. GitHub에 빈 저장소 about-me를 만들고 push한다.
힌트 보기
  1. 5절 따라하기 순서를 떠올립니다. 폴더 만들기 → 저장소 만들기 → 한 줄 쓰기 → add → commit을 세 번 되풀이합니다.
  2. Git Bash에서 D:\workspace는 /d/workspace로 씁니다. 원격 연결과 첫 push는 7절의 git remote add origin ...과 git push -u origin main을 씁니다.
  3. 함정: GitHub에서 저장소를 만들 때 README 추가를 체크하지 않습니다. 체크하면 원격에 커밋이 하나 생겨 첫 push가 거절됩니다. git commit -am은 이미 Git이 아는 파일의 수정만 add까지 한 번에 합니다. 새 파일은 반드시 git add를 먼저 합니다.
  4. 확인하는 법: git log --oneline에 커밋 3줄이 보이고, GitHub 저장소 화면에 README.md의 세 줄이 보이면 성공입니다.

문제 2 (필수) — 충돌 만들고 해결하기

about-me 저장소에서 아래 순서로 충돌을 만들고 해결하세요.

  1. feature/goal 브랜치에서 목표 줄을 목표: 백엔드 개발자로 바꾸고 커밋한다.
  2. main으로 돌아와 같은 줄을 목표: 풀스택 개발자로 바꾸고 커밋한다.
  3. main에서 feature/goal을 merge하고 충돌을 해결한다. 최종 값은 목표: 풀스택 백엔드 개발자로 한다.
힌트 보기
  1. 브랜치 만들기와 이동은 6절의 git switch -c와 git switch를 씁니다. 두 브랜치에서 같은 줄을 다르게 고쳐야 충돌이 납니다.
  2. CONFLICT (content): Merge conflict in README.md가 나오면 8절 따라하기처럼 VS Code나 메모장으로 README.md를 엽니다. <<<<<<<, =======, >>>>>>> 사이에 두 브랜치의 내용이 나란히 보입니다.
  3. 함정: 표시 세 줄을 하나라도 남기고 커밋하면 그 글자가 그대로 기록에 남습니다. 고친 뒤 git add → git commit 전에 git diff --staged로 확인합니다. 해결을 포기하려면 git merge --abort로 merge 전으로 돌아갑니다.
  4. 확인하는 법: README.md에 목표: 풀스택 백엔드 개발자 한 줄만 남고, git log --oneline --graph에 두 갈래가 하나로 합쳐진 모양이 보이면 성공입니다.

문제 3 (필수) — 팀 저장소에 첫 PR

조직의 우리 팀 저장소에서 docs/members/내아이디.md 파일을 추가하는 PR을 올리세요. 파일에는 이름과 맡고 싶은 역할을 적습니다.

힌트 보기
  1. 순서는 9절의 GitHub Flow입니다. clone → 새 브랜치 → 파일 추가와 커밋 → 브랜치 push → PR → 리뷰 → Merge.
  2. 팀 저장소는 7절의 git clone으로 받고, 브랜치 이름은 docs/member-내아이디처럼 하는 일이 보이게 짓습니다. push 결과에 나오는 PR 링크나 GitHub 화면의 Compare & pull request 버튼으로 PR을 엽니다. PR 템플릿(9절)을 채우고 팀원 한 명을 리뷰어로 지정합니다.
  3. 함정: main에 직접 push하면 보호 규칙 때문에 거절됩니다(10절). 정상입니다. 반드시 브랜치를 push합니다. Merge한 뒤에는 내 PC의 main도 git pull로 최신으로 맞추고, 다 쓴 브랜치는 지웁니다.
  4. 확인하는 법: GitHub의 PR 화면에 Merged 표시가 보이고, 팀 저장소의 docs/members/ 폴더에 내 파일이 보이면 성공입니다. 팀원이 모두 서로 다른 파일을 추가하므로 충돌은 나지 않습니다.

문제 4 (생각) — 상태 읽기

아래 git status 결과를 보고 세 파일이 각각 어느 영역에 있는지, 다음에 무엇을 해야 하는지 말하세요.

On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   README.md

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   app.js

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        notes.txt
힌트 보기
  1. 4절의 세 영역(작업 폴더 · 스테이징 · 저장소) 그림을 옆에 두고 봅니다. git status는 제목 세 개로 파일을 나눠 보여 줍니다.
  2. 제목마다 뜻을 우리말로 바꿔 봅니다. "to be committed", "not staged", "Untracked"가 각각 무슨 뜻인지 생각하면 영역이 보입니다. 괄호 안의 (use "git ...") 안내도 다음 할 일의 큰 힌트입니다.
  3. 함정: 추적하지 않는 파일이 모두 올려야 할 파일은 아닙니다. 개인 메모라면 11절의 .gitignore를 떠올립니다.
  4. 확인하는 법: "지금 바로 git commit을 하면 어떤 파일이 사진에 들어가나?"에 답할 수 있으면 다 푼 것입니다.

문제 5 (도전) — .env를 올려 버렸다

방금 외부 서비스 키(API_KEY=abc123...)가 든 .env 파일을 커밋해 팀 저장소에 push했습니다. 해야 할 일을 순서대로 쓰고, 각 단계의 이유를 설명하세요.

힌트 보기
  1. 무엇이 진짜 위험한지부터 생각합니다. 파일일까요, 그 안의 키일까요? 올라간 순간 누가 볼 수 있었는지 떠올립니다.
  2. 앞으로 Git이 .env를 추적하지 않게 하는 방법은 11절의 .gitignore와 git rm --cached입니다. --cached가 내 PC의 파일을 지우는지, 기록에서만 빼는지 확인합니다.
  3. 함정: 파일을 지우고 새로 커밋해도 이전 커밋의 사진에는 키가 그대로 남습니다. 기록 자체를 고치는 작업은 팀원 모두의 저장소에 영향을 주므로 혼자 하지 않습니다. 누구에게 먼저 알려야 할지도 순서에 넣습니다.
  4. 확인하는 법: 순서마다 "왜 이 단계가 이 자리에 오는가"를 한 문장으로 쓸 수 있으면 됩니다. 마지막에 git status를 쳤을 때 .env가 목록에 나오지 않아야 합니다. 참고: GitHub Docs — 저장소에서 민감한 데이터 제거
