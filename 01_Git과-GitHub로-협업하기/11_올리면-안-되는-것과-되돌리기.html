1장. Git과 GitHub로 협업하기

올리면 안 되는 것과 되돌리기 — .gitignore · restore · revert

준비시간1시간개념 지도작업 폴더 → 원격 저장소 전체

한 줄 요약

한 번 올린 것은 지워도 기록에 남습니다. 그래서 비밀번호, 키, 빌드 결과물은 .gitignore로 처음부터 안 올립니다. 이미 올린 커밋을 취소할 때는 기록을 지우지 않고 "취소하는 새 커밋"(revert)을 찍습니다.

1. .gitignore — Git이 모른 척할 목록

저장소 맨 위에 .gitignore 파일을 두면, 거기 적힌 파일은 git status에도 안 나오고 git add .를 해도 들어가지 않습니다.

# 빌드 결과물
build/
out/
node_modules/
dist/

# IDE 설정
.idea/
.vscode/
*.iml

# 비밀 정보
.env
application-secret.yml
*.pem

팀 프로젝트 저장소에는 강사가 이 파일을 미리 넣어 둡니다. 새 도구를 쓰기 시작하면 팀이 함께 목록을 늘립니다.

비밀번호·API 키는 한 번 커밋해 올리면 지워도 기록(과거 사진)에 남습니다. 올렸다면 지우는 것으로 끝나지 않고, 그 키를 즉시 폐기하고 새로 발급해야 합니다.

GitHub는 2024년 3월부터 개인 계정의 새 공개 저장소에서 비밀 정보 푸시 차단(push protection)을 기본으로 켭니다(조직 저장소는 강사가 켭니다). 하지만 모든 비밀을 잡지는 못합니다. .gitignore가 먼저입니다. (GitHub Changelog 2024-03-11)

2. 상황별 되돌리기

상황 명령 결과
고친 파일을 마지막 커밋 상태로 git restore 파일 수정이 사라진다 (되찾을 수 없음)
add한 것을 다시 빼기 git restore --staged 파일 수정은 남고, 상자에서만 꺼낸다
이미 push한 커밋 취소 git revert 커밋번호 그 커밋을 취소하는 새 커밋이 생긴다
이미 커밋한 파일을 추적에서만 빼기 git rm --cached 파일 내 PC의 파일은 남고, Git만 더 이상 추적하지 않는다

따라하기 — git rm --cached

.gitignore에 적어도 이미 추적 중인 파일은 계속 추적됩니다. .env를 먼저 커밋해 버리고 뒤늦게 .gitignore에 .env를 적었다면, 추적에서 따로 빼야 합니다. 그 상황을 my-first-repo에서 만들어 봅니다.

$ echo "DB_PASSWORD=test1234" > .env
$ git add .env
$ git commit -m "chore: 설정 파일 추가"
$ echo ".env" > .gitignore
$ git status

실행 결과

On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        .gitignore

nothing added to commit but untracked files present (use "git add" to track)

.gitignore에 적었는데도 .env에 대해서는 아무 말이 없습니다. 이미 추적 중이라 그대로 추적된다는 뜻입니다. 추적에서 빼야 합니다.

$ git rm --cached .env
$ git status

실행 결과

rm '.env'
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        deleted:    .env

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        .gitignore

deleted:는 Git 기록에서만 빠진다는 뜻이고, 폴더의 .env 파일은 그대로 있습니다. git add .gitignore → git commit -m "chore: .env 추적 제외"로 마무리하면 그 뒤로는 .env가 git status에 나오지 않습니다. 이미 push한 커밋에는 내용이 남아 있다는 점은 1절과 같습니다.

따라하기 — revert

$ printf '특기: 없음\n' >> README.md
$ git commit -am "docs: 특기 추가"
$ git revert --no-edit HEAD
$ git log --oneline

실행 결과

[main a77a94a] Revert "docs: 특기 추가"
 1 file changed, 1 deletion(-)
a77a94a (HEAD -> main) Revert "docs: 특기 추가"
2ee6451 docs: 특기 추가
56b15e6 merge: 목표 충돌 해결

HEAD는 "지금 브랜치의 가장 최근 커밋"입니다. --no-edit는 메시지 편집 창을 띄우지 않고 기본 메시지를 쓰라는 옵션입니다.

3. reset은 왜 쓰지 않나

인터넷에서 git reset --hard를 자주 보게 됩니다. reset은 기록 자체를 지웁니다. 내 PC에만 있는 커밋이라면 괜찮지만, 이미 팀원이 받아 간 커밋을 지우면 팀원의 기록과 어긋나 큰 혼란이 생깁니다.

공유한 커밋은 revert로 취소한다. 기록은 그대로 두고 "취소했다"는 사진을 하나 더 찍는 방식이라 팀원 기록이 망가지지 않습니다.

핵심 정리

  • .gitignore로 빌드 결과물, IDE 설정, 비밀 정보를 처음부터 막는다.
  • 비밀을 올렸다면 지우는 게 아니라 폐기·재발급이다.
  • 커밋 전 수정 버리기는 restore, 공유한 커밋 취소는 revert, 이미 커밋한 파일을 추적에서만 빼기는 rm --cached.
  • reset --hard는 공유한 커밋에 쓰지 않는다.
