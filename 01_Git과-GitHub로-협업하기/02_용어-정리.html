1장. Git과 GitHub로 협업하기

용어 정리 — 이 장에서 처음 만나는 말

준비시간40분개념 지도전체 흐름

이 절을 읽는 법

이 장에서 처음 만나는 용어들입니다. 앞으로 과정 내내 쓰이므로 여기서 정확히 잡고 갑니다. 개발이 처음이라면 이 절이 가장 낯설 수 있습니다. 완벽히 외울 필요는 없습니다. "이런 게 있구나" 정도로 눈에 익혀 두면 실습하면서 자연스럽게 손에 붙습니다.

이 절은 두 부분으로 나뉩니다.

부분 내용 읽는 법
1~4 터미널, 셸, CLI, 경로, 명령어 읽는 법 Git 이전에 필요한 도구 이야기. 처음이라면 꼼꼼히
5~9 버전 관리, 저장소, 커밋, 브랜치, GitHub 용어 Git 이야기. 뒤 절에서 자세히 배우므로 뜻만

1. 터미널(Terminal)과 셸(Shell)

터미널은 마우스 클릭 대신 글자로 명령을 입력해서 컴퓨터를 조작하는 창입니다. 폴더를 만들고, 프로그램을 실행하고, 파일을 옮기는 일을 모두 문장으로 시킬 수 있습니다. Git을 비롯한 개발 도구의 상당수가 터미널에서 실행되므로, 개발을 하려면 터미널과 친해져야 합니다.

'터미널'이라는 이름의 유래를 알면 기억에 남습니다. 옛날 대형 컴퓨터 시절, 사람들은 방 하나를 차지하는 중앙 컴퓨터에 단말기(terminal)라는 화면과 키보드를 연결해 명령을 주고받았습니다. 그 단말기 화면을 흉내 낸 프로그램이 오늘날의 터미널입니다. 그래서 지금도 콘솔(console), 명령 프롬프트(command prompt), 커맨드 라인(command line)이 거의 같은 뜻으로 쓰입니다.

셸(shell)은 사용자가 입력한 명령을 해석해 운영체제에 전달하고 실행하는 프로그램입니다. 이름은 운영체제의 핵심(커널)을 감싸는 '껍데기(shell)'라는 뜻에서 왔습니다.

정리: 터미널은 명령을 입력하고 결과를 보는 창, 셸은 그 명령을 해석해 실행하는 프로그램입니다.

셸에도 종류가 있습니다.

셸 어디에 비고
bash / zsh macOS·리눅스 기본 개발 현장에서 널리 쓰입니다. macOS는 zsh가 기본이며 bash와 사용법이 거의 같습니다
PowerShell / CMD Windows 기본 명령 문법이 bash와 다릅니다
Git Bash Windows에 Git을 설치하면 함께 설치됨 Windows에서 bash를 쓸 수 있게 해 줍니다. 이 과정의 표준 셸
  • bash는 'Bourne-Again SHell'의 말장난입니다. 유닉스 초창기의 Bourne shell을 잇는다는 뜻과 '다시 태어난(born again) 셸'이라는 뜻을 겹쳐 지은 이름입니다. (GNU Bash 매뉴얼)
  • zsh는 macOS가 2019년(Catalina)부터 기본 셸로 쓰고 있습니다. 이 과정의 Git 명령은 zsh에서도 그대로 동작합니다. (Apple 지원)

왜 Windows에서 굳이 Git Bash를 쓰나요? 두 가지 이유입니다.

  1. 인터넷의 Git 자료와 명령 예시는 대부분 bash 기준입니다. 같은 "폴더 만들기"도 PowerShell과 bash는 문법이 다릅니다. 모두가 bash를 쓰면 강의 자료 하나로 통일됩니다.
  2. 나중에 배우는 서버(리눅스)와 Docker도 bash 명령을 씁니다. 지금 익힌 명령을 그대로 다시 씁니다.

2. CLI와 GUI

터미널에서 글자로 실행하는 프로그램을 CLI(Command Line Interface, 명령 줄 인터페이스)라고 부릅니다. 마우스로 아이콘을 눌러 쓰는 프로그램인 GUI(Graphical User Interface, 그래픽 사용자 인터페이스)와 대비되는 말입니다.

GUI CLI
조작 버튼·메뉴·창을 보고 마우스로 글자로 명령
배우기 쉽다 처음엔 어렵다
장점 한눈에 보인다 빠르고, 정확하고, 기록하고 반복하기 쉽다
예 웹 브라우저, 워드, IntelliJ의 Git 버튼 Git Bash의 git 명령

"이 폴더의 파일 300개 이름을 한 번에 바꿔라" 같은 일은 마우스로는 300번 클릭이지만 CLI로는 한 줄입니다. 그리고 명령은 글자라서 채팅창에 붙여 넣어 질문하거나, 팀원에게 그대로 전달할 수 있습니다. 온라인 수업에서 "제 화면은 이렇게 나와요"를 정확히 공유하기 좋습니다.

이 과정은 Git을 CLI로 먼저 배웁니다. IntelliJ나 VS Code의 Git 버튼(GUI)은 안에서 같은 git 명령을 대신 실행합니다. 명령을 알면 버튼이 무슨 일을 하는지 알 수 있지만, 버튼만 알면 문제가 생겼을 때 손을 쓸 수 없습니다.

3. 경로(Path)와 현재 위치

경로는 파일이나 폴더가 어디 있는지 알려 주는 주소입니다. 탐색기 주소창에 보이는 D:\workspace\my-first-repo가 경로입니다.

터미널은 항상 어느 한 폴더 안에 서 있습니다. 이것을 현재 위치(작업 디렉터리, working directory)라고 합니다. 명령은 현재 위치를 기준으로 실행됩니다. git init을 엉뚱한 폴더에서 치면 엉뚱한 폴더가 저장소가 됩니다. 그래서 "지금 내가 어디 있지?"를 확인하는 습관이 가장 중요합니다.

Windows와 Git Bash는 같은 주소를 다르게 씁니다.

의미 Windows 탐색기 Git Bash
D 드라이브의 workspace 폴더 D:\workspace /d/workspace
내 사용자 폴더(홈) C:\Users\내계정 ~
폴더 구분 기호 \ (역슬래시) / (슬래시)

자주 쓰는 기호와 명령입니다.

기호·명령 뜻 예
pwd 지금 어디 있는지 보기 (print working directory) /d/workspace
ls 지금 폴더 안의 파일 목록 (ls -a는 숨김 파일까지) .git은 -a를 붙여야 보입니다
cd 폴더 그 폴더로 이동 (change directory) cd my-first-repo
cd .. 한 단계 위 폴더로 ..은 "위 폴더"
. 지금 이 폴더 git add . = 지금 폴더 전부
mkdir 이름 폴더 만들기 (make directory) mkdir my-first-repo
  • 절대 경로: 맨 위부터 전부 쓴 주소. /d/workspace/my-first-repo
  • 상대 경로: 현재 위치에서부터 쓴 주소. 지금 /d/workspace에 있다면 my-first-repo만 써도 됩니다.

예시: 현재 위치가 /d/workspace일 때, 상대 경로 my-first-repo/README.md와 절대 경로 /d/workspace/my-first-repo/README.md는 같은 파일입니다.

4. 명령어 읽는 법

Git 명령은 모양이 일정합니다. 한 번 읽는 법을 익히면 처음 보는 명령도 대략 짐작할 수 있습니다.

$ git commit -m "docs: 자기소개 추가"
git commit -m "docs: 자기소개 추가"
프로그램 하위 명령 옵션 옵션에 넘기는 값
부분 뜻 예
프로그램 어떤 프로그램에게 시키나 git
하위 명령 무엇을 하라는가 commit, add, push
옵션 어떻게 하라는가. -로 시작 -m(메시지를 바로 적는다)
값(인자) 대상이나 내용 README.md, "메시지"
  • 옵션은 짧은 형태(-m)와 긴 형태(--message)가 있습니다. 뜻은 같습니다. --global, --oneline처럼 긴 형태만 있는 옵션도 있습니다.
  • 띄어쓰기가 들어간 값은 따옴표로 감쌉니다. -m 첫 커밋이라고 쓰면 Git은 "첫"까지만 메시지로 읽습니다.
  • 모르는 명령은 git 하위명령 -h로 짧은 도움말을 볼 수 있습니다. 예: git commit -h

명령을 치기 전에 "무엇을, 어디서, 어떻게"를 읽습니다. 프로그램(git) · 하위 명령(무엇을) · 현재 위치(어디서) · 옵션(어떻게).

5. 버전 관리와 Git

버전 관리(Version Control)는 파일이 바뀌어 온 기록을 남기고, 필요하면 예전 상태로 돌아갈 수 있게 해 주는 일입니다. 보고서_최종.hwp, 보고서_최종_진짜최종.hwp처럼 파일을 복사해 두는 것도 일종의 버전 관리입니다. 다만 누가, 언제, 왜 바꿨는지 알 수 없고, 여러 명이 동시에 고치면 합치기가 어렵습니다. 이 일을 프로그램이 대신 해 주는 것이 버전 관리 시스템(VCS, Version Control System)이고, 지금 가장 많이 쓰는 것이 Git입니다.

Git: 파일의 변경 사항을 추적하고, 여러 사람이 같은 파일로 하는 작업을 조율하는 분산 버전 관리 시스템.

  • 유래: Git은 2005년 리눅스를 만든 리누스 토르발스가 리눅스 개발에 쓰려고 만들었습니다. 그전에 쓰던 상용 도구를 더 이상 무료로 쓸 수 없게 되자 직접 만든 것입니다. (Pro Git 1.2 — Git의 짧은 역사)
  • 이름: Git 공식 설명서에는 토르발스가 이 도구를 "멍청한 내용 추적기(the stupid content tracker)"라고 불렀고, 이름은 기분에 따라 "발음하기 쉬운 세 글자", "영국 속어로 멍청이", "Global Information Tracker의 줄임말"로 읽어도 된다고 적혀 있습니다. (Git README)
  • 분산형: Git은 모든 사람의 PC에 전체 기록이 통째로 복사되는 분산형입니다. 그래서 인터넷이 없어도 커밋할 수 있고, 서버가 고장 나도 누군가의 PC에 기록이 남아 있습니다. 예전에 많이 쓰던 SVN은 기록이 서버 한 곳에만 있는 중앙집중형입니다.

6. 저장소(Repository)와 로컬·원격

용어 뜻 자세히
저장소 (repository, 줄여서 repo) Git이 기록을 관리하는 프로젝트 폴더. 안에 숨김 폴더 .git이 있고, 여기에 모든 기록이 들어 있습니다 5절
로컬 저장소 내 PC에 있는 저장소 5절
원격 저장소 (remote) 인터넷(GitHub)에 있는 저장소. 팀이 함께 씁니다 7절
origin 원격 저장소에 붙이는 기본 별명. clone하면 자동으로 붙습니다. 주소 대신 origin이라고 부릅니다 (Pro Git 2.5) 7절
clone 원격 저장소를 기록째 내 PC로 복사하기 7절
push / pull 내 커밋을 원격에 올리기 / 원격의 새 커밋을 받아 와 합치기 7절
fetch 원격의 새 커밋을 받아만 오기 (합치지 않음) 7절

7. 커밋, 스테이징, 커밋 번호

용어 뜻 자세히
커밋 (commit) 특정 시점의 프로젝트 파일 상태를 저장한 기록(스냅샷). 누가, 언제, 왜(메시지) 저장했는지가 함께 남습니다 4절
작업 폴더 (working tree) 지금 내가 고치고 있는 파일들 4절
스테이징 (staging, add) 다음 커밋에 넣을 변경을 고르는 단계 4절
커밋 메시지 이 커밋을 왜 만들었는지 적는 한 줄. 예: docs: 자기소개 추가 9절
커밋 번호 (해시, hash) 커밋마다 붙는 40글자 고유 번호. 보통 앞 7글자(932e50d)만 씁니다 5절
diff 두 상태 사이에 바뀐 줄. +는 추가, -는 삭제 5절

커밋 번호는 커밋 내용(파일, 작성자, 시간, 메시지 등)으로 계산한 고유 값(SHA-1 해시)입니다. 내용이 한 글자라도 다르면 번호가 완전히 달라집니다. 그래서 같은 실습을 해도 사람마다 커밋 번호가 다릅니다. 교안의 번호와 달라도 정상입니다. (Pro Git 1.3 — Git은 데이터의 무결성을 보장한다)

8. 브랜치, HEAD, main

용어 뜻 자세히
브랜치 (branch) 커밋 하나를 가리키는 이름(포인터). 새 커밋을 만들면 그 커밋을 가리키도록 자동으로 옮겨 갑니다 6절
main 저장소의 기본 브랜치 이름. 늘 잘 동작하는 상태로 둡니다 6절
HEAD "지금 내가 보고 있는 곳"을 가리키는 표시. 보통 지금 브랜치를 가리킵니다 6절
merge 두 브랜치의 작업을 하나로 합치기 6절
충돌 (conflict) 같은 줄을 서로 다르게 고쳐서, Git이 사람에게 골라 달라고 하는 상태 8절
태그 (tag) 특정 커밋에 붙인 고정된 이름. 새 커밋을 만들어도 옮겨 가지 않습니다. 강사 코드 단계 표시에 씁니다 12절

main과 master: 예전에는 기본 브랜치 이름이 master였습니다. 2020년부터 GitHub를 비롯한 여러 곳이 main으로 바꾸기 시작했고, 지금 GitHub에서 새로 만든 저장소의 기본 브랜치는 main입니다. Git 프로그램 자체는 아직 master가 기본이라서, 3절에서 main으로 맞추는 설정을 합니다. 오래된 자료에서 master가 보이면 main과 같은 역할이라고 읽으면 됩니다. (GitHub — renaming)

9. GitHub에서 만나는 말

용어 뜻 자세히
GitHub Git 저장소를 인터넷에 올려 두고 팀이 함께 쓰는 웹 서비스. Git과는 다른 회사의 서비스입니다 1절
Pull Request (PR) "내 브랜치의 변경을 가져가서(pull) main에 합쳐 주세요"라는 요청서. 이 위에서 코드 리뷰를 합니다 9절
코드 리뷰 합치기 전에 팀원이 코드를 읽고 의견을 남기는 일 9절
Issue 할 일, 버그, 아이디어를 적어 두는 게시판 글. 번호(#12)로 부릅니다 9절
Organization 여러 사람과 저장소를 묶어 관리하는 단체 계정. 이 과정의 팀 저장소가 여기에 있습니다 10절
.gitignore Git이 모른 척할 파일 목록. 비밀번호, 빌드 결과물을 여기에 적습니다 11절
2단계 인증 (2FA) 비밀번호에 더해 휴대폰 앱 코드로 한 번 더 확인하는 로그인 방식 3절

실무 참고: GitLab은 같은 기능을 Merge Request(MR)라고 부릅니다. 국내 회사 중에는 사내에 GitLab을 설치해 쓰는 곳도 많습니다. 이름만 다르고 하는 일은 PR과 같습니다. (GitLab Docs — Merge requests)

핵심 정리

  • 터미널은 명령을 입력하는 창, 셸은 명령을 해석해 실행하는 프로그램이다. 이 과정의 셸은 Git Bash다.
  • 명령은 현재 위치에서 실행된다. 헷갈리면 pwd.
  • 명령은 프로그램 하위명령 옵션 값 순서로 읽는다.
  • Git은 기록 도구(내 PC), GitHub는 기록을 함께 쓰는 서비스(인터넷)다.
  • 커밋은 특정 시점의 저장 기록, 브랜치는 커밋을 따라 옮겨 가는 이름, 태그는 고정된 이름이다.
