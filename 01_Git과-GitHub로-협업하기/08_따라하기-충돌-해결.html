1장. Git과 GitHub로 협업하기

따라하기 — 충돌은 고장이 아니라 대화 요청

준비시간2시간개념 지도두 갈림길이 만나는 곳 (merge)

한 줄 요약

충돌(conflict)은 두 사람이 같은 파일의 같은 줄을 다르게 고쳤을 때만 생깁니다. Git이 어느 쪽이 맞는지 모르니 사람에게 묻는 것입니다. 표시를 읽고, 원하는 모습으로 고치고, 다시 커밋하면 끝입니다.

1. 혼자서 충돌 만들어 보기

my-first-repo에서 두 브랜치가 같은 줄을 다르게 고치게 만듭니다. 파일은 편집기로 직접 열어 고칩니다.

편집기 여는 법: 탐색기에서 README.md를 오른쪽 클릭 → 연결 프로그램 → 메모장 또는 VS Code. Git Bash에서 notepad README.md(메모장)나 code README.md(VS Code)로 열어도 됩니다.

① feature/a 브랜치에서 고치기

$ git switch -c feature/a

README.md를 열어 목표: 풀스택 개발자 줄을 아래처럼 고치고 저장한 뒤 편집기를 닫습니다.

목표: 백엔드 개발자

$ git diff
$ git commit -am "docs: 목표를 백엔드로"

git diff에서 -목표: 풀스택 개발자, +목표: 백엔드 개발자 두 줄이 보이면 제대로 고친 것입니다.

② main 브랜치에서 같은 줄을 다르게 고치기

$ git switch main

README.md를 다시 열면 목표: 풀스택 개발자로 돌아와 있습니다. 브랜치를 바꾸면 폴더의 파일도 그 브랜치의 내용으로 바뀌기 때문입니다. 이번에는 아래처럼 고치고 저장한 뒤 닫습니다.

목표: 프론트엔드 개발자

$ git commit -am "docs: 목표를 프론트로"

③ 합치기

$ git merge feature/a

git commit -am은 "이미 Git이 아는 파일의 수정을 add하고 바로 커밋"입니다. 새 파일에는 쓸 수 없습니다.

브랜치를 바꾸기 전에 편집기에서 저장하고 닫습니다. 파일을 연 채로 브랜치를 바꾸면, 편집기에 예전 내용이 남아 있다가 그대로 다시 저장될 수 있습니다.

실행 결과

Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

2. 충돌 표시 읽기

$ cat README.md

# 자기소개

이름: 나학생
<<<<<<< HEAD
목표: 프론트엔드 개발자
=======
목표: 백엔드 개발자
>>>>>>> feature/a
취미: 등산
표시 뜻
<<<<<<< HEAD ~ ======= 지금 내 브랜치(main)의 내용
======= ~ >>>>>>> feature/a 합치려는 브랜치(feature/a)의 내용
표시 바깥 줄 (취미: 등산) 충돌 없이 자동으로 합쳐진 부분

충돌 해결 = 표시 세 줄(<<<<<<<, =======, >>>>>>>)을 지우고, 남길 내용을 사람이 정하는 것. 한쪽만 남겨도, 둘을 섞어도 됩니다.

3. 고치고 마무리하기

편집기로 README.md를 열어 아래처럼 고칩니다. 표시 세 줄은 반드시 지웁니다.

# 자기소개

이름: 나학생
목표: 풀스택 개발자 (프론트엔드 + 백엔드)
취미: 등산

$ git add README.md
$ git commit -m "merge: 목표 충돌 해결"
$ git log --oneline --graph

실행 결과

*   56b15e6 (HEAD -> main) merge: 목표 충돌 해결
|\  
| * f4be624 (feature/a) docs: 목표를 백엔드로
* | 12a371f docs: 목표를 프론트로
|/  
* 73ed024 (feature/hobby) docs: 취미 추가
* 310a2ea chore: 메모 삭제
* 5c1d0b7 docs: 메모 추가
* ef983ad docs: 목표 추가
* 932e50d docs: 자기소개 README 추가

두 갈림길이 하나로 합쳐진 모양이 보입니다. 7절 실습을 같은 저장소에서 했다면 커밋과 origin/main 표시가 더 보일 수 있습니다.

해결하다가 꼬였다면 git merge --abort로 merge 직전 상태로 돌아갈 수 있습니다.

4. 다 같이 충돌 겪기 — 팀 파일 실습

과정 Organization에 practice-conflict 저장소를 만들어 두었습니다. 안에는 팀마다 파일이 하나씩 있습니다(team-1.md ~ team-6.md). 내 팀 파일만 고칩니다. 아래는 3팀(team-3.md)의 예시입니다.

# 3팀 멤버

(여기에 한 줄 소개)

같은 팀원 모두가 같은 3번째 줄에 자기소개를 써서 Pull Request를 엽니다. 팀에서 첫 PR이 합쳐지는 순간, 같은 팀의 나머지 PR에는 모두 충돌이 생깁니다. 다른 팀의 파일은 건드리지 않으므로 팀 사이에는 충돌이 나지 않습니다.

$ cd /d/workspace
$ git clone https://github.com/<조직이름>/practice-conflict.git
$ cd practice-conflict
$ git switch -c intro/내아이디
# team-3.md 3번째 줄을 "나학생 — 백엔드가 궁금해서 왔습니다" 처럼 고친다
$ git commit -am "docs: 나학생 자기소개"
$ git push -u origin intro/내아이디

GitHub에서 Pull Request를 엽니다(9절). 팀에서 순서를 정해 한 번에 한 PR씩 합칩니다. 첫 PR은 충돌 없이 합쳐집니다. 그 뒤 나머지 팀원의 PR에는 "This branch has conflicts that must be resolved"가 나옵니다. 내 PC에서 해결합니다.

$ git pull origin main

실행 결과 (From ...으로 시작하는 줄은 생략)

Auto-merging team-3.md
CONFLICT (content): Merge conflict in team-3.md
Automatic merge failed; fix conflicts and then commit the result.

team-3.md를 열면 1절과 같은 표시가 보입니다. HEAD 쪽은 내 소개, 반대쪽은 먼저 합쳐진 팀원의 소개입니다. 브랜치 이름 자리에 긴 커밋 번호가 나오는 것은 origin의 main을 받아서 합쳤기 때문입니다.

# 3팀 멤버

<<<<<<< HEAD
나학생 — 백엔드가 궁금해서 왔습니다
=======
김팀원 — 프론트엔드에 관심이 있습니다
>>>>>>> 602c2f94d058b128984a4b75a6cbcd40f4c2c074

표시 세 줄을 지우고 두 사람 소개가 모두 남도록 고칩니다. 먼저 합쳐진 팀원을 위에 둡니다.

# 3팀 멤버

김팀원 — 프론트엔드에 관심이 있습니다
나학생 — 백엔드가 궁금해서 왔습니다

$ git add team-3.md
$ git commit -m "merge: main 반영, 자기소개 충돌 해결"
$ git push

push하면 PR이 자동으로 갱신되고 충돌 표시가 사라집니다. 팀원이 이 PR을 합치면, 다음 사람이 같은 순서로 되풀이합니다. 팀원이 늘수록 남길 줄도 늘어납니다.

확인하는 법: 팀원 전원의 PR이 합쳐진 뒤 git switch main → git pull로 받은 team-3.md에 팀원 수만큼 소개 줄이 있고, <<<<<<< 같은 표시가 한 줄도 없으면 성공입니다.

핵심 정리

  • 충돌은 같은 파일의 같은 줄을 다르게 고쳤을 때만 생긴다.
  • <<<<<<< 위는 내 것, >>>>>>> 앞은 합치려는 것.
  • 표시를 지우고 남길 내용을 정한 뒤 add → commit.
  • 꼬이면 git merge --abort.
